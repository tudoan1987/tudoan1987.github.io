GitOps với ArgoCD:
Deploy Kubernetes không còn lo sợ

Tu Doan Minh Nov 2025 8 min read

Trước khi dùng GitOps, mỗi lần deploy production là một sự kiện căng thẳng — ai đó chạy kubectl apply trên laptop, không ai biết cluster đang ở trạng thái gì, rollback là một mớ lệnh gõ tay trong panic. Sau khi migrate sang ArgoCD, deploy trở thành boring — và đó chính xác là điều bạn muốn.

GitOps là gì (và không phải là gì)

GitOps = Git là single source of truth cho infrastructure và application state. Bất kỳ thay đổi nào trên cluster đều phải đi qua Git commit — không có exception.

  • ✅ Developer push code → CI build image → update image tag trong Git → ArgoCD sync
  • ❌ Không ai được kubectl edit hay helm upgrade trực tiếp trên production
Nếu bạn vẫn còn kubectl apply -f trực tiếp lên production, bạn chưa làm GitOps — bạn đang làm "Git lưu file YAML".

App of Apps Pattern

Thay vì tạo từng ArgoCD Application thủ công, dùng App of Apps để quản lý mọi app từ một repo trung tâm: 

gitops-repo/
├── apps/                        # App of Apps root
│   ├── Chart.yaml
│   ├── values-dev.yaml
│   ├── values-staging.yaml
│   ├── values-prod.yaml
│   └── templates/
│       ├── api-service.yaml
│       ├── frontend.yaml
│       ├── worker.yaml
│       └── monitoring.yaml
└── services/                    # Actual service configs
    ├── api-service/
    │   ├── dev/
    │   ├── staging/
    │   └── prod/
    └── frontend/
        └── ...
# apps/templates/api-service.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-service-{{ .Values.environment }}
  namespace: argocd
  finalizers:
  - resources-finalizer.argocd.argoproj.io
spec:
  project: {{ .Values.environment }}
  source:
    repoURL: https://github.com/company/gitops-repo
    targetRevision: HEAD
    path: services/api-service/{{ .Values.environment }}
  destination:
    server: {{ .Values.clusterUrl }}
    namespace: api-service
  syncPolicy:
    automated:
      prune: true          # xóa resources không còn trong Git
      selfHeal: true       # auto-revert manual changes trên cluster
    syncOptions:
    - CreateNamespace=true
    - PrunePropagationPolicy=foreground

Promotion Flow: Dev → Staging → Prod

CI pipeline chỉ update image tag trong Git — ArgoCD làm phần còn lại: 

# .github/workflows/deploy.yml
- name: Update image tag in GitOps repo
  run: |
    git clone https://github.com/company/gitops-repo
    cd gitops-repo

    # Dev: auto-deploy sau mỗi merge vào main
    yq e '.image.tag = "${{ github.sha }}"' \
      -i services/api-service/dev/values.yaml

    git add .
    git commit -m "chore: deploy api-service ${{ github.sha }} to dev"
    git push

    # Staging: chỉ deploy khi có tag vX.Y.Z
    if [[ "${{ github.ref }}" == refs/tags/v* ]]; then
      yq e '.image.tag = "${{ github.sha }}"' \
        -i services/api-service/staging/values.yaml
      git add . && git commit -m "chore: promote to staging" && git push
    fi

Production promotion là manual — tạo PR vào prod/ branch, cần 2 approvals: 

# Branch protection rules cho gitops-repo/prod branch:
# - Require pull request reviews: 2
# - Require status checks: staging-smoke-tests
# - Restrict who can push: only release-bot + SRE team

Automated Rollback

ArgoCD không tự rollback khi app unhealthy — cần thêm logic. Tôi dùng ArgoCD Notifications + custom webhook: 

# argocd-notifications-cm.yaml
triggers:
  - name: on-degraded
    condition: app.status.health.status == 'Degraded'
    template: rollback-on-degraded

templates:
  - name: rollback-on-degraded
    webhook:
      rollback-service:
        method: POST
        path: /rollback
        body: |
          {
            "app": "{{.app.metadata.name}}",
            "revision": "{{.app.status.sync.revision}}"
          }
# rollback-service — revert Git commit và push
def rollback(app_name: str, failed_revision: str):
    repo = git.Repo("gitops-repo")

    # Tìm commit trước đó còn healthy
    last_good = find_last_healthy_revision(app_name, failed_revision)

    # Revert trong Git — ArgoCD sẽ sync về trạng thái đó
    repo.git.revert(failed_revision, no_edit=True)
    repo.remote("origin").push()

    notify_slack(f"🔄 Rolled back {app_name} to {last_good[:8]}")

Secrets trong GitOps với Sealed Secrets

Secret không được commit plain text vào Git. Tôi dùng Bitnami Sealed Secrets — encrypt bằng cluster public key, chỉ cluster đó mới decrypt được: 

# Encrypt secret trước khi commit
kubeseal --format yaml \
  --controller-name=sealed-secrets \
  --controller-namespace=kube-system \
  < secret.yaml > sealed-secret.yaml

# sealed-secret.yaml an toàn để commit vào Git
git add sealed-secret.yaml
git commit -m "feat: add db credentials for api-service"

Kết quả sau 1 năm dùng GitOps

  • Deploy frequency tăng 3x — deploy nhiều hơn vì ít sợ hơn
  • MTTR (Mean Time to Recovery) từ 45 phút xuống 8 phút
  • Zero "surprise" cluster state — mọi thứ đều có trong Git history
  • Onboarding engineer mới: từ 2 tuần học deploy process xuống 2 ngày
  • Audit trail hoàn chỉnh — biết chính xác ai deploy gì, lúc nào, tại sao

GitOps không phải tool — là văn hoá. ArgoCD chỉ là enforcement mechanism. Thứ quan trọng hơn là team đồng ý: Git là sự thật, không phải cluster.
