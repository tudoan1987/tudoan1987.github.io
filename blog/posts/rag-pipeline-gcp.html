RAG Pipeline trên GCP:
Bài học từ Production RAG Pipeline on GCP:
Lessons from Production

Tu Doan Minh Apr 2026 8 min read

Sau 3 tháng vận hành hệ thống RAG (Retrieval-Augmented Generation) trên GCP cho một khách hàng enterprise, tôi muốn chia sẻ những gì thực sự xảy ra khi bạn đưa một LLM pipeline vào production — không phải demo notebook, mà là hệ thống xử lý 50,000+ query/ngày.

Sai lầm #1: Tin tưởng cosine similarity quá mức

Ban đầu tôi dùng pure vector search với cosine similarity, top-k=3. Kết quả trên dev dataset rất ổn, nhưng khi production traffic vào, precision giảm rõ rệt — đặc biệt với các câu hỏi có nhiều negatives.

Giải pháp: chuyển sang hybrid search (dense + sparse BM25) và thêm cross-encoder reranking. Latency tăng ~120ms nhưng relevance score cải thiện 18% theo user feedback.

Đừng skip reranking — nó là thứ tạo ra sự khác biệt giữa "hoạt động được" và "thực sự tốt".

Sai lầm #2: Chunk size cố định

Chunk 512 tokens nghe có vẻ hợp lý. Nhưng với documents có cấu trúc phức tạp (bảng, code, danh sách), fixed-size chunking phá vỡ context một cách tàn nhẫn. Tôi chuyển sang semantic chunking:

from langchain_experimental.text_splitter import SemanticChunker
from langchain_google_vertexai import VertexAIEmbeddings

embeddings = VertexAIEmbeddings(model_name="text-embedding-004")
splitter = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=90
)

Tối ưu latency: từ 2.4s xuống 780ms

1. Semantic cache với Redis

Cache response dựa trên embedding similarity (threshold = 0.92). Cache hit rate đạt 34% sau 1 tuần — giảm đáng kể LLM calls.

Kết luận

RAG không phải là "thêm vector DB rồi gọi LLM". Phần khó không phải code — mà là hiểu data của bạn, iterate retrieval strategy, và build observability ngay từ đầu. Nếu bạn đang bắt đầu: invest time vào chunking và reranking trước.

After three months running a RAG (Retrieval-Augmented Generation) system on GCP for an enterprise client, here's what actually happens when you put an LLM pipeline into production — not a demo notebook, but a system handling 50,000+ queries per day.

Mistake #1: Over-trusting cosine similarity

I started with pure vector search using cosine similarity, top-k=3. Results on the dev dataset looked great, but when production traffic hit, precision dropped noticeably — especially on questions with many negative candidates.

The fix: switch to hybrid search (dense + sparse BM25) and add a cross-encoder reranker. Latency increased ~120ms but relevance score improved 18% based on user feedback.

Don't skip reranking — it's the difference between "it works" and "it actually works well".

Mistake #2: Fixed chunk sizes

512 tokens sounds reasonable. But for documents with complex structure (tables, code, lists), fixed-size chunking brutally destroys context. I switched to semantic chunking:

from langchain_experimental.text_splitter import SemanticChunker
from langchain_google_vertexai import VertexAIEmbeddings

embeddings = VertexAIEmbeddings(model_name="text-embedding-004")
splitter = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=90
)

Takeaways

RAG is not "add a vector DB then call an LLM". The hard part isn't the code — it's understanding your data, iterating on retrieval strategy, and building observability from day one. If you're starting out: invest time in chunking and reranking first.
