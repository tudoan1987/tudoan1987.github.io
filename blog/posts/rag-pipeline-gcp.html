RAG Pipeline trên GCP:
Bài học từ Production

Tu Doan Minh Apr 2026 8 min read

Sau 3 tháng vận hành hệ thống RAG (Retrieval-Augmented Generation) trên GCP cho một khách hàng enterprise, tôi muốn chia sẻ những gì thực sự xảy ra khi bạn đưa một LLM pipeline vào production — không phải demo notebook, mà là hệ thống xử lý 50,000+ query/ngày.

Kiến trúc tổng quan

Stack cuối cùng sau nhiều lần iterate:

  • LLM: Gemini 1.5 Pro qua Vertex AI
  • Vector DB: Weaviate trên GKE (self-hosted)
  • Orchestration: LangChain + custom retrieval logic
  • Embedding: text-embedding-004 (Vertex AI)
  • Cache: Redis (Memorystore) cho semantic caching
  • Serving: FastAPI trên Cloud Run

Sai lầm #1: Tin tưởng cosine similarity quá mức

Ban đầu tôi dùng pure vector search với cosine similarity, top-k=3. Kết quả trên dev dataset rất ổn, nhưng khi production traffic vào, precision giảm rõ rệt — đặc biệt với các câu hỏi có nhiều negatives.

Giải pháp: chuyển sang hybrid search (dense + sparse BM25) và thêm cross-encoder reranking. Latency tăng ~120ms nhưng relevance score cải thiện 18% theo user feedback.

Đừng skip reranking — nó là thứ tạo ra sự khác biệt giữa "hoạt động được" và "thực sự tốt".

Sai lầm #2: Chunk size cố định

Chunk 512 tokens nghe có vẻ hợp lý. Nhưng với documents có cấu trúc phức tạp (bảng, code, danh sách), fixed-size chunking phá vỡ context một cách tàn nhẫn.

Tôi chuyển sang semantic chunking — chia dựa trên sentence embeddings similarity, không dựa trên token count. Document loader pipeline: 

from langchain_experimental.text_splitter import SemanticChunker
from langchain_google_vertexai import VertexAIEmbeddings

embeddings = VertexAIEmbeddings(model_name="text-embedding-004")
splitter = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=90
)

docs = splitter.create_documents([raw_text])

Tối ưu latency: từ 2.4s xuống 780ms

Breakdown latency ban đầu:

  • Embedding query: 180ms
  • Vector search: 95ms
  • Reranking: 340ms
  • LLM generation: 1,800ms

Những thay đổi giảm latency nhiều nhất:

1. Semantic cache với Redis

Cache response dựa trên embedding similarity thay vì exact match. Threshold = 0.92 cosine similarity. Cache hit rate đạt 34% sau 1 tuần — giảm đáng kể LLM calls.

2. Streaming response

Dù total latency không đổi, perceived latency giảm mạnh khi stream tokens về client. Time-to-first-token từ 1.8s xuống còn ~400ms.

3. Async embedding + search

Query rewriting và embedding chạy concurrent thay vì sequential: 

async def retrieve(query: str) -> list[Document]:
    rewritten, embedding = await asyncio.gather(
        rewrite_query(query),
        embed_query(query)
    )
    return await hybrid_search(rewritten, embedding)

Monitoring trong production

Metrics quan trọng nhất tôi track trên Cloud Monitoring + Grafana:

  • Retrieval precision@k — tỷ lệ relevant docs trong top-k results
  • Answer faithfulness — LLM có hallucinate không (dùng Ragas framework)
  • Cache hit rate — efficiency của semantic cache
  • P95 latency — theo từng component trong pipeline
  • Token usage — cost tracking per request type

Kết luận

RAG không phải là "thêm vector DB rồi gọi LLM". Phần khó không phải code — mà là hiểu data của bạn, iterate retrieval strategy, và build observability ngay từ đầu.

Nếu bạn đang bắt đầu một RAG project: invest time vào chunking và reranking, đừng để đến khi vào production mới nhận ra vấn đề.
