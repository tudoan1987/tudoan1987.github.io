MLflow + Kubernetes:
MLOps Pipeline từ A đến Z

Tu Doan Minh Feb 2026 10 min read

"Model của tôi train xong rồi, giờ deploy lên production như thế nào?" — câu hỏi này tôi nghe ít nhất một lần mỗi tuần. Bài này là câu trả lời đầy đủ: một MLOps platform tôi đã build và vận hành thực tế, từ experiment đến production monitoring.

Kiến trúc tổng thể

┌─────────────────────────────────────────────────────┐
│                   ML Platform                        │
│                                                     │
│  Data      Training     Registry    Serving         │
│  ─────     ────────     ────────    ───────         │
│  Feature   MLflow       MLflow      KServe          │
│  Store     Tracking     Model       (Istio)         │
│  (Feast)   + Runs       Registry    + Canary        │
│                                                     │
│  Monitoring: Prometheus + Grafana + Evidently       │
└─────────────────────────────────────────────────────┘

MLflow trên Kubernetes

MLflow tracking server deploy trên K8s với PostgreSQL backend và S3/GCS artifact store: 

# mlflow-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mlflow-tracking
  namespace: mlops
spec:
  replicas: 2
  selector:
    matchLabels:
      app: mlflow-tracking
  template:
    spec:
      containers:
      - name: mlflow
        image: ghcr.io/mlflow/mlflow:2.11.0
        args:
          - mlflow
          - server
          - --host=0.0.0.0
          - --port=5000
          - --backend-store-uri=postgresql://$(DB_USER):$(DB_PASS)@postgres:5432/mlflow
          - --default-artifact-root=gs://my-mlflow-artifacts
          - --serve-artifacts
        envFrom:
        - secretRef:
            name: mlflow-secrets

Model Registry và Promotion Flow

Model chỉ được promote lên production qua một pipeline có gate rõ ràng:

  • Staging: F1 > 0.90, không có bias vi phạm fairness threshold
  • Production Canary: 5% traffic, monitor 24h
  • Production Full: auto-promote nếu error rate < 0.1% và latency P95 < 200ms
# Promote model qua MLflow API
import mlflow

client = mlflow.MlflowClient()

# Tìm run tốt nhất
best_run = client.search_runs(
    experiment_ids=["1"],
    filter_string="metrics.val_f1 > 0.90",
    order_by=["metrics.val_f1 DESC"],
    max_results=1
)[0]

# Register và promote
mv = client.create_model_version(
    name="fraud-detector",
    source=best_run.info.artifact_uri + "/model",
    run_id=best_run.info.run_id
)
client.transition_model_version_stage(
    name="fraud-detector",
    version=mv.version,
    stage="Staging"
)

Canary Deployment với KServe + Istio

KServe InferenceService hỗ trợ canary natively — chỉ cần thay đổi canaryTrafficPercent: 

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: fraud-detector
  namespace: production
spec:
  predictor:
    model:
      modelFormat:
        name: sklearn
      storageUri: gs://models/fraud-detector/v2
  canaryTrafficPercent: 10
  canary:
    predictor:
      model:
        modelFormat:
          name: sklearn
        storageUri: gs://models/fraud-detector/v3

Drift Detection và Auto-rollback

Dùng Evidently AI để monitor data drift và prediction drift theo giờ. Khi PSI > 0.2, tự động trigger rollback qua ArgoCD: 

from evidently.report import Report
from evidently.metric_preset import DataDriftPreset

def check_drift_and_rollback(reference_data, current_data):
    report = Report(metrics=[DataDriftPreset()])
    report.run(reference_data=reference_data, current_data=current_data)

    result = report.as_dict()
    drift_score = result["metrics"][0]["result"]["dataset_drift"]

    if drift_score:
        # Trigger ArgoCD rollback via API
        requests.post(
            "https://argocd.internal/api/v1/applications/fraud-detector/rollback",
            headers={"Authorization": f"Bearer {ARGOCD_TOKEN}"},
            json={"revision": get_last_stable_revision()}
        )
        send_alert(f"Model rollback triggered — drift detected")
Auto-rollback đã cứu production 2 lần trong 6 tháng đầu vận hành — một lần do data pipeline thay đổi schema, một lần do seasonal drift không lường trước.

Lessons Learned

  • Feature store (Feast) là investment đáng giá — loại bỏ training/serving skew ngay từ đầu
  • Log input data cùng với prediction — không có nó, debug production issues gần như impossible
  • Canary nhỏ (5-10%) ít nhất 24h trước khi full rollout — đừng vội
  • Model governance: mọi production model phải có owner, expiry date và fallback plan
