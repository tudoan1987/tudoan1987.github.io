Terraform Best Practices
cho Multi-cloud Infrastructure Terraform Best Practices
for Multi-cloud Infrastructure

Tu Doan Minh Jan 2026 7 min read

Sau 6 năm viết Terraform — từ những file main.tf 2000 dòng đến monorepo với 80+ modules — tôi muốn chia sẻ những pattern thực sự hoạt động khi scale lên multi-cloud, multi-team.

Cấu trúc thư mục

infrastructure/
├── modules/                  # Reusable modules
│   ├── networking/
│   ├── kubernetes/
│   └── observability/
├── cloud/
│   ├── aws/environments/{dev,staging,prod}/
│   ├── gcp/environments/...
│   └── azure/environments/...
└── _bootstrap/               # Remote state backends
Tách modules/ ra khỏi environments/ ngay từ đầu — đây là quyết định khó sửa nhất nếu để sau.

Remote State với Locking

terraform {
  backend "s3" {
    bucket         = "company-tfstate-prod"
    key            = "aws/prod/terraform.tfstate"
    region         = "ap-southeast-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
    kms_key_id     = "arn:aws:kms:..."
  }
}

Module Versioning

module "vpc" {
  source = "git::https://github.com/company/tf-modules.git//aws/vpc?ref=v2.4.1"
  cidr_block         = "10.0.0.0/16"
  availability_zones = ["ap-southeast-1a", "ap-southeast-1b", "ap-southeast-1c"]
}

Secrets Management — Không bao giờ hardcode

data "vault_generic_secret" "db_creds" {
  path = "secret/prod/database"
}
resource "aws_db_instance" "main" {
  username = data.vault_generic_secret.db_creds.data["username"]
  password = data.vault_generic_secret.db_creds.data["password"]
}

Tôi không dùng Workspaces

Terraform Workspaces nghe hay nhưng trong thực tế gây confusion. Tôi prefer separate directories + separate state files — mỗi environment là một thư mục riêng biệt, không có nguy cơ apply nhầm environment.

Những điều tôi ước biết sớm hơn

  • Đừng import resources thủ công — viết code từ đầu, dù mất thêm 2 tiếng
  • Tag mọi thứ ngay từ commit đầu tiên — sửa sau rất đau
  • Chạy terraform plan trong CI — không bao giờ apply local trong production
  • Pin provider versions: ~> 5.0 không phải >= 5.0

After six years writing Terraform — from 2,000-line main.tf files to a monorepo with 80+ modules — here are the patterns that actually work when scaling to multi-cloud, multi-team.

Directory structure

infrastructure/
├── modules/                  # Reusable modules
│   ├── networking/
│   ├── kubernetes/
│   └── observability/
├── cloud/
│   ├── aws/environments/{dev,staging,prod}/
│   ├── gcp/environments/...
│   └── azure/environments/...
└── _bootstrap/               # Remote state backends
Separate modules/ from environments/ from the start — this is the hardest decision to fix later.

Remote state with locking

terraform {
  backend "s3" {
    bucket         = "company-tfstate-prod"
    key            = "aws/prod/terraform.tfstate"
    region         = "ap-southeast-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
    kms_key_id     = "arn:aws:kms:..."
  }
}

Module versioning

module "vpc" {
  source = "git::https://github.com/company/tf-modules.git//aws/vpc?ref=v2.4.1"
  cidr_block         = "10.0.0.0/16"
  availability_zones = ["ap-southeast-1a", "ap-southeast-1b", "ap-southeast-1c"]
}

Secrets management — never hardcode

data "vault_generic_secret" "db_creds" {
  path = "secret/prod/database"
}
resource "aws_db_instance" "main" {
  username = data.vault_generic_secret.db_creds.data["username"]
  password = data.vault_generic_secret.db_creds.data["password"]
}

Why I don't use Workspaces

Terraform Workspaces sound appealing but cause confusion in practice. I prefer separate directories + separate state files — each environment is its own directory, eliminating the risk of applying to the wrong environment.

Things I wish I'd known earlier

  • Don't import resources manually — write code from scratch, even if it takes an extra two hours
  • Tag everything from the very first commit — retrofitting tags is painful
  • Always run terraform plan in CI — never apply locally in production
  • Pin provider versions: ~> 5.0 not >= 5.0
