Terraform Best Practices
cho Multi-cloud Infrastructure

Tu Doan Minh Jan 2026 7 min read

Sau 6 năm viết Terraform — từ những file main.tf 2000 dòng đến monorepo với 80+ modules — tôi muốn chia sẻ những pattern thực sự hoạt động khi scale lên multi-cloud, multi-team.

Cấu trúc thư mục

Pattern tôi dùng hiện tại cho codebase có 3 cloud và 5 environment: 

infrastructure/
├── modules/                  # Reusable modules (no cloud-specific)
│   ├── networking/
│   ├── kubernetes/
│   └── observability/
├── cloud/
│   ├── aws/
│   │   ├── modules/          # AWS-specific modules
│   │   └── environments/
│   │       ├── dev/
│   │       ├── staging/
│   │       └── prod/
│   ├── gcp/
│   │   └── environments/...
│   └── azure/
│       └── environments/...
├── global/                   # DNS, CDN, cross-cloud resources
└── _bootstrap/               # Remote state backends (run once)
Tách modules/ ra khỏi environments/ ngay từ đầu — đây là quyết định khó sửa nhất nếu để sau.

Remote State với Locking

Mỗi environment có state riêng, không bao giờ share state giữa environments: 

# backend.tf — prod AWS
terraform {
  backend "s3" {
    bucket         = "company-tfstate-prod"
    key            = "aws/prod/terraform.tfstate"
    region         = "ap-southeast-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
    kms_key_id     = "arn:aws:kms:ap-southeast-1:123456789:key/abc123"
  }
}

# Cross-cloud state reference — đọc output từ AWS state trong GCP config
data "terraform_remote_state" "aws_vpc" {
  backend = "s3"
  config = {
    bucket = "company-tfstate-prod"
    key    = "aws/prod/terraform.tfstate"
    region = "ap-southeast-1"
  }
}

# Dùng VPC CIDR từ AWS để config GCP VPC peering
locals {
  aws_vpc_cidr = data.terraform_remote_state.aws_vpc.outputs.vpc_cidr
}

Module Versioning

Modules được version qua git tags — không dùng source = "../../../modules/networking" trong production: 

module "vpc" {
  source  = "git::https://github.com/company/tf-modules.git//aws/vpc?ref=v2.4.1"

  cidr_block          = "10.0.0.0/16"
  availability_zones  = ["ap-southeast-1a", "ap-southeast-1b", "ap-southeast-1c"]
  enable_nat_gateway  = true
  single_nat_gateway  = var.environment != "prod"
}

Secrets Management — Không bao giờ hardcode

Rule tuyệt đối: không có secret nào trong Terraform state hoặc code. Pattern tôi dùng với HashiCorp Vault: 

provider "vault" {
  address = "https://vault.internal:8200"
  auth_login {
    path = "auth/kubernetes/login"
    parameters = {
      role = "terraform-prod"
      jwt  = file("/var/run/secrets/kubernetes.io/serviceaccount/token")
    }
  }
}

data "vault_generic_secret" "db_creds" {
  path = "secret/prod/database"
}

resource "aws_db_instance" "main" {
  username = data.vault_generic_secret.db_creds.data["username"]
  password = data.vault_generic_secret.db_creds.data["password"]
  # password không bao giờ lưu vào state vì dùng sensitive = true
}

Workspace Strategy — Tôi không dùng Workspaces

Terraform Workspaces nghe hay nhưng trong thực tế gây confusion. Tôi prefer separate directories + separate state files:

  • Mỗi environment là một thư mục riêng biệt
  • Không có nguy cơ terraform apply nhầm environment
  • Dễ dàng có config khác nhau giữa dev và prod mà không cần count tricks
  • State isolation hoàn toàn — blast radius của một incident nhỏ hơn

CI/CD Pipeline cho Terraform

# .github/workflows/terraform.yml
jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - name: Terraform Format Check
      run: terraform fmt -check -recursive

    - name: Terraform Validate
      run: terraform validate

    - name: tfsec Security Scan
      uses: aquasecurity/tfsec-action@v1.0.0

    - name: Infracost — Cost Estimate
      uses: infracost/actions/setup@v3
      with:
        api-key: ${{ secrets.INFRACOST_API_KEY }}

    - name: Terraform Plan
      run: terraform plan -out=tfplan

    - name: Post Plan to PR
      uses: actions/github-script@v7
      # Comment plan output vào PR để review

Những điều tôi ước biết sớm hơn

  • Đừng import resources thủ công — viết code từ đầu, dù mất thêm 2 tiếng
  • Tag mọi thứ ngay từ commit đầu tiên — sửa sau rất đau
  • Chạy terraform plan trong CI — không bao giờ apply local trong production
  • Dùng moved block khi rename resource — tránh destroy/recreate không cần thiết
  • Pin provider versions — ~> 5.0 không phải >= 5.0
